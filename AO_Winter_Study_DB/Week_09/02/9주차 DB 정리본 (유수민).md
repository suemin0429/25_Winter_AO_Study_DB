# 배달의 민족: 모놀리식의 한계 극복과 MSA 기반 DB 분리 실무 적용에 대한 케이스 스터디

→ 유튜브(우아콘 등)에 공개된 배달의민족 기술 진화 과정을 통해 대규모 트래픽을 감당해야 하는 최신 IT 환경에서 왜 시스템과 DB를 분리해야만 했는지, 그리고 실무에서는 어떤 아키텍처(MSA, CQRS, Redis)로 이 문제를 해결하고 있는지를 분석한다.

- MSA 기반 DB 분리란? 데이터베이스 퍼 서비스 패턴으로 핵심은 시스템을 독립적으로 배포 가능한 작은 단위로 나누는 것이다. loose coulping을 달성하기 위해 각 마이크로서비스가 자신만의 전용 데이터베이스를 가지도록 물리적, 놀리적으로 격리하는 설계 패턴을 데이터베이스 퍼 서비스 라고 한다.
- bounded context(바운디드 컨텍스트): 도메인 주도 설계(DDD, Domain-Driven Design)에 따라 나누어진 비즈니스 경계 내에서만 데이터를 응집시킨다.
- data encapsulation(데이터 캡슐화): 타 도메인의 데이터가 필요할 경우, 오직 해당 서비스가 제공하는 공식 API를 통해서만 접근 권한을 가진다.

## 1. 거대 모놀리식 단일 DB의 붕괴 (초창기 ~ 2015년)

초창기 배달의 민족은 빠른 시장 진입을 위해 루비 온 레일즈(Ruby on Rails)와 PHP 등으로 만들어진 전형적인 거대 모놀리식(Monolithic) 시스템이었다. 당시 아키텍처의 가장 큰 특징은 단 하나의 거대한 관계형 데이터베이스(RDBMS, 주로 MS SQL Server나 MySQL)에 모든 데이터가 집중되어 있었다는 점이다.

'가게 정보', '사용자 정보', '주문 내역', '결제 내역', '리뷰', '라이더 배차 정보' 등등 수백 개의 테이블이 하나의 DB 안에서 거미줄처럼 얽혀 있었다. 트래픽이 적을 때는 문제가 없었지만 배달 앱 특유의 극단적인 트래픽 스파이크(금요일 저녁 6시, 비 오는 날, 복날, 월드컵 등)가 발생하자 이 구조는 대재앙을 불러오게 되었다.

### 실무에서 맞닥뜨린 3가지 치명적 인프라 장애 원인

**① DB 커넥션 풀(Connection Pool) 고갈과 쓰레드 풀(Thread Pool)의 연쇄 붕괴**
트래픽이 몰리면 클라우드 환경(AWS)에서 웹 애플리케이션 서버(WAS)를 오토 스케일링(Auto Scaling)으로 10대에서 100대로 순식간에 늘릴 수 있다. 하지만 문제는 맨 뒤에 버티고 있는 단일 DB는 스케일 아웃(Scale-out, 수평 확장)이 불가능**하다**는 점이었다.
수백 대의 서버가 하나의 DB와 통신하기 위해 커넥션을 시도하지만 DB가 열어둘 수 있는 커넥션의 개수는 물리적으로 한정되어 있다. 결국 커넥션을 얻지 못한 서버의 요청들은 대기열에 쌓이게 되고 서버의 쓰레드 풀마저 꽉 차버리면서 시스템 전체가 멈춰버리는 장애가 발생하게 된다.

**② 단일 장애점(SPOF, Single Point of Failure)과 장애의 전파(Cascading Failure)**
이것이 우아콘에서 가장 강조하는 부분이다. 금요일 저녁, 사람들이 일제히 결제를 시도하면서 DB의 '주문/결제 테이블'에 락이 걸리고 응답이 지연된다.
그런데 DB가 하나다 보니 자원(CPU, Memory)을 공유하게 되고 결제와는 전혀 상관없이 구경만 하던 고객의 앱 화면마저 무한 로딩에 빠지게 되었다. 하나의 기능 장애가 앱 전체의 마비로 번지는 장애 전파 구조가 가장 큰 문제점이었다.

**③ 조인(JOIN) 쿼리의 늪과 스키마 변경의 두려움 (사이드 이펙트)**
모든 테이블이 한곳에 있으니, 개발자들은 ‘회원 테이블 JOIN 주문 테이블 JOIN 가게 테이블 JOIN 리뷰 테이블’ 등 수십 개를 엮어 무거운 쿼리를 날리고 있었다. 쿼리 한 방이면 데이터를 가져오니 개발은 편했지만 DB 성능은 바닥을 치고 있었던 것이다. 게다가 테이블 하나에 컬럼을 하나 추가하려고 해도 이 테이블을 참조하는 다른 수십 개의 서비스에서 어떤 사이드 이펙트(Side Effect)가 터질지 몰라 아무도 DB 스키마를 건드리지 못하는 레거시의 늪에 빠지게 되었다.

- 사이드 이펙트: A를 수정했는데 상관없는 B나 C가 고장나는 현상을 뜻한다. 공유 데이터베이스 환경에서는 이 사이드 이펙트가 시스템을 마비시키는 주범이 된다. 즉, 테이블을 여러 서비스가 공유하고 있으면(Tight Coupling) 테이블 구조를 조금만 변경해도 이를 참조하는 다른 수십 개의 시스템 중 어디서 에러가 터질지 아무도 예측이 불가능하다.
- 레거시: 오래전에 개발되어 낡고 복잡하지만 회사의 핵심 비즈니스를 돌리고 있어서 버릴 수도 없고 고치기도 두려운 과거의 시스템이나 코드를 말한다.

## 2. MSA 전환과 Database per Service (2016년 ~ 2019년)

김영한 개발자를 비롯한 배민 인프라팀은 Java와 Spring Framework(Spring Boot) 기반으로 시스템을 완전히 새로 짜게 된다. 핵심은 시스템을 기능별로 잘게 쪼개는 마이크로서비스 아키텍처(MSA)의 전면 도입이었다.

### 도메인 주도 설계(DDD)와 Bounded Context

배민은 도메인 주도 설계(Domain Driven Design, DDD) 방법론을 도입하여 비즈니스 영역을 철저히 분석했다. '가게 노출(전시)', '주문', '결제', '리뷰', '라이더 배차' 등을 각각 독립적인 바운디드 컨텍스트(Bounded Context)로 정의하고 별도의 프로젝트로 분리했다.

- 도메인 주도 설계 DDD란? 시스템을 가장 완벽하게 쪼개는 기준이자 철학이다.
- 바운디드 컨텍스트란? 특정 도메인의 언어와 규칙이 완벽하게 적용되는 물리적, 논리적인 울타리를 의미한다.

### 가짜 MSA를 피하는 법: DB의 물리적 완벽 분리

API 서버만 쪼개고 DB는 여전히 하나를 공유한다면 그것은 분산된 모놀리식(Distributed Monolithic)일 뿐, 진짜 MSA가 아니다. 배민은 Database per Service = 분리된 개별 DB 패턴을 엄격하게 적용했다.

- 물리적 격리: 주문 서버는 오직 주문 DB(AWS Aurora MySQL 등)만 바라보고 결제 서버는 오직 결제 DB만 바라보게 되었다. 다른 도메인의 DB에는 방화벽 레벨에서 접근을 원천 차단했다.
- API를 통한 통신 (API Composition): 이제 DB 레벨에서의 JOIN 쿼리는 물리적으로 불가능해졌다. 만약 주문 내역 화면에서 가게 이름과 결제 금액을 같이 보여줘야 한다면?
    - 주문 서버가 1) 가게 서버의 API를 HTTP나 gRPC로 호출해서 가게 이름을 가져오고, 2) 결제 서버의 API를 호출해 결제 금액을 가져와서 3) 애플리케이션(Spring) 메모리 단에서 데이터를 Composition(조합)하여 프론트엔드로 내려주는 방식으로 패러다임이 완전히 바뀌었다.

### MSA 분리의 궁극적 목적 → 장애 격리 (Fault Isolation) 달성

이렇게 개발 복잡도가 올라가는 것을 감수하면서까지 DB를 쪼갠 이유는 단 하나, 장애 격리 때문이다.
이제 피크타임에 결제 DB가 터져도 사용자는 여전히 가게 DB를 통해 메뉴를 구경하고 장바구니에 담을 수 있게 되었다. 또한, 리뷰 DB가 응답이 없으면 시스템 전체가 죽는 대신 서킷 브레이커(Circuit Breaker)가 작동하여 리뷰 영역만 "일시적으로 리뷰를 불러올 수 없습니다"라는 폴백(Fallback: 대체 응답) 화면을 띄웁니다. 최소한 고객 경험이 완전히 무너지는 것을 막아낸 것이다.

- 서킷 브레이커란? A서비스가 B서비스를 호출할 때 B서비스의 상태가 불안정하여 타임아웃이나 에러가 지속적으로 발생하면 A 서비스 내부에 있는 서킷 브레이커가 이를 감지하고 B로 향하는 네트워크 연결을 강제로 끊어버리는 것이다.
    - closed - 정상 상태(닫힘) : API 요청이 정상적으로 타켓 서버로 흘러가는 상태
    - open - 장애 발생(열림, 차단) : 타겟 서버에서 에러율이나 타임아웃 횟수가 설정한 임계치를 넘어서면 회로가 열림
    - half-open - 반개방(복구 테스트) : 일정 시간이 지나면 서킷 브레이커가 스스로 회로를 반쯤 닫고 테스트용 요청 몇개만 타겟 서버로 흘려보냄
- 폴백이란? 서킷 브레이커가 open 상태가 되어 API 호출이 차단되었을 때 고객의 스마트폰 화면에 에러를 바로 띄울 수는 없다. 이때 고객 경험을 방어하기 위해 준비해 둔 대체 응답이 폴백이다.
    - graceful degradation (우아한 성능 저하): 시스템의 일부 기능이 고장 났을 때 전체 시스템을 마비시키지 않고 기능의 수준을 부드럽게 낮추어 핵심 서비스는 계속 유지하겠다는 분산 시스템의 철학이다. 폴백은 이 철학을 구현하는 구체적인 기술 중 하나이다.

## 3. 전시 도메인 : 쏟아지는 Read 트래픽과 CQRS, Redis의 도입 (2020년 ~ 현재)

DB를 기능별로 찢어 장애를 격리하는 데는 성공했지만 새로운 병목이 찾아오게 되었다. 고객이 앱을 켜자마자 마주하는 가게 노출(전시) 도메인의 트래픽이다.

배달 앱의 트래픽을 분석해 보면, 사용자는 결제(Write)를 한 번 하기 위해 메뉴판 스크롤, 리뷰 확인, 가게 검색 등 조회(Read) ****트래픽을 수십~수백 번 발생시킨다. (Read/Write 비율의 극단적 불균형 상태) 분리해 놓은 가게 DB가 이 엄청난 조회 쿼리(Read)를 다 받아내다 보니 또다시 CPU 사용률이 100%를 치며 병목현상이 생긴 것이다.

### CQRS (명령과 조회의 책임 분리) 아키텍처의 전면 도입

우아콘 "B마트 전시 도메인 CQRS 적용기" 등에서 가장 핵심적으로 다루는 아키텍처이다. 배민은 ‘RDBMS는 무거운 쓰기 작업과 데이터의 무결성을 지키는 데만 쓰고 단순 조회는 완전히 다른 곳에서 처리하자’ 는 결론을 내립니다. 이것이 **CQRS(Command and Query Responsibility Segregation)** 패턴입니다.

CQRS는 시스템의 상태를 변경하는 명령 작업을 처리하는 모델과 시스템의 상태를 반환하는 조회 작업을 처리하는 모델을 아키텍처 레벨에서 완벽하게 분리하는 소프트웨어 설계 패턴이다. 전통적인 시스템에서는 데이터베이스 트랜잭션을 처리하기 위해 단일 도메인 모델 하나로 쓰기와 읽기를 모두 처리한다. 시스템의 규모가 커진다면 쿼리가 극도로 복잡해지고 ORM의 성능 병목이 발생한다. 따라서 이러한 장애를 해결하기 위해서 도입하는 것이다.

- **Command Model (명령/쓰기 전용 저장소):** 수정하거나 새로운 메뉴를 추가하는 무거운 작업은 트랜잭션과 무결성이 보장된 기존 RDBMS(가게 메인 DB)에서 처리한다. 트랜잭션의 안전성과 데이터 무결성을 보장하기 위함이다. 도메인의 상태를 변경하고 변경된 사실을 이벤트 형태로 발행하는 역학을 수행한다.
- **Query Model (조회/읽기 전용 저장소):** 요청하는 작업은 RDBMS로 보내지 않고 앞단에 구축해 둔 레디스에서 전담하여 처리하게 만든다. 대규모 동시 조회 트래픽에 대한 극단적인 응답 속도를 보장하기 위함이다. 프론트엔드가 요구하는 뷰의 형태에 맞춰 데이터가 사전에 조립 및 역정규화되어 저장된다. 이를 구체화된 뷰(materialized view) 패턴이라고 부른다.

### Redis: 단순 캐시를 넘어선 메인 조회 저장소

이 엄청난 조회를 감당하기 위해 투입된 것이 바로 인메모리(In-Memory) NoSQL인 Redis(레디스)다. 여기서 중요한 실무 용어가 등장하게 된다. 바로 ‘구체화된(Materialized)’는 표현이다.

1. **이벤트 기반 동기화 :** 사장님이 RDBMS에서 메뉴 가격을 수정하면 RDBMS는 "메뉴가 변경되었다"는 이벤트 메시지를 발생시킨다.
2. **워커(Worker) 노드의 조립 :** 이 이벤트를 감지한 백그라운드 서버(Worker)가 RDBMS에서 최신 데이터를 긁어와서 프론트엔드(모바일 앱)가 화면에 그리기 가장 좋은 형태의 거대한 JSON 문서로 데이터를 조립한다.
3. **Redis에 구체화 :** 가공이 끝난 JSON 데이터를 Redis에 저장한다.
4. **초고속 응답 :** 이제 고객이 앱을 켜서 메뉴판을 볼 때는 무거운 RDBMS를 건드릴 필요가 없다. 앞단에 있는 Redis에서 이미 다 구체화된 JSON 데이터를 뽑아서 보여주기만 하면 된다.

이러한 Redis 캐시 히트(Cache Hit) 전략 덕분에 메인 DB로 향하는 조회 트래픽의 대부분을 방어해 냈고 피크 시간대에도 버벅거림 없는 쾌적한 앱 환경을 구축할 수 있었다.

## 4. 분산 환경의 그림자: 데이터 정합성과 다음 세대의 아키텍처 (결론 및 Next Step)

지금까지의 모놀리식 분해 ➔ Database per Service 기반 MSA ➔ CQRS와 Redis 도입을 통해 배달의 민족은 천만 트래픽을 견딜 수 있는 견고한 인프라를 완성했다.

하지만 서버가 죽는 것은 막아냈지만, DB를 물리적으로 찢어놓고 레디스라는 다른 저장소까지 섞어 쓰다 보니 개발자들을 극한의 스트레스로 몰아넣는 가장 치명적인 문제가 수면 위로 떠올랐다. 바로 분산 환경에서의 데이터 정합성(Data Consistency) 문제이다.

- **동기화 지연 (Eventual Consistency의 부작용):** 사장님이 RDBMS에서 '치킨 품절' 버튼을 눌렀는데 순간적인 네트워크 지연으로 레디스에는 '품절' 상태가 2초 늦게 업데이트되었다고 가정해 보자. 하필 그 2초 사이에 고객이 앱을 켜면 품절 안 된 치킨이 보이고 결제까지 해버리는 아찔한 CS(고객 서비스) 대참사가 발생한다.
- **분산 트랜잭션 숙제 :** 과거 단일 DB 시절에는 하나의 트랜잭션 안에서 BEGIN ➔ 주문 성공 처리 ➔ 결제 성공 처리 ➔ COMMIT (실패 시 한 번에 ROLLBACK)이 아주 쉽게 가능했다.
하지만 이제는 주문 DB와 결제 DB가 다르다. 주문 서버가 주문 DB에 '주문 완료'를 기록하고 결제 서버의 API를 호출했는데 결제 서버 쪽에서 Timeout 에러가 나버리면? 이미 완료 처리된 주문 DB의 데이터를 어떻게 되돌릴까? DB가 다르니 ROLLBACK 명령어도 먹히지 않는다.

바로 이 거대한 숙제를 해결하기 위해, 현재 배달의민족, 토스(Toss), 네이버 등 최상위 IT 기업들은 아파치 카프카(Apache Kafka)를 활용한 이벤트 주도 아키텍처(EDA)와 실패 시 반대되는 작업을 실행해 데이터를 맞추는 보상 트랜잭션(Compensating Transaction) 기반의 사가(Saga) 패턴이라는 초고도화된 차세대 기술을 속속 도입하고 있다.

## 케이스 스터디 요약 및 시사점

이 케이스 스터디를 통해 우리는 데이터베이스 설계가 단순히 테이블을 어떻게 예쁘게 짤 것인가의 문제를 넘어서 서비스의 생존과 대규모 트래픽 방어라는 인프라적 관점과 직결된다는 것을 확인할 수 있었다.
모놀리식의 한계를 인지하고, MSA로 DB를 분리하며, CQRS와 레디스로 읽기 성능을 극대화하는 일련의 과정은 현재 모든 유니콘 급 IT 기업들이 밟고 있는 필수적인 진화의 로드맵이다. 하지만 다중 DB가 항상 정답이라는 것은 아니기에 자신과 기업이 현재 속한 상황을 잘 인지하여 모놀리식을 선택할지 다중 DB를 선택할지 고민해야 한다.
